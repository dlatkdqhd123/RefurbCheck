# 서명된 검사 자료 업데이트 — v1.3

RefurbCheck 1.3은 APK를 다시 설치하지 않고 공개 악성·감시 파일 참조 자료를 갱신할 수 있습니다. 앱 실행 시 전경에서 Wi-Fi로 확인하는 설정, 수동 인터넷 확인, Android 파일 선택기를 통한 서명된 ZIP 가져오기를 지원합니다. 앱 목록·APK·검사 결과를 서버로 보내지 않습니다. GitHub는 일반적인 다운로드 접속 정보(IP 주소 등)를 받습니다.

이 기능은 **자료 배포자가 서명한 정확한 해시 목록**을 갱신합니다. 백신 엔진을 원격으로 설치하거나 임의 스크립트를 실행하지 않습니다. 새로운 파일 지문을 배포하지 않은 기간, 파일이 바뀐 변종, 실행 중 내려받는 페이로드를 자동으로 학습하는 기능은 아닙니다.

## 사용자에게 보이는 동작

1. 시작 화면의 **검사 자료 업데이트**에서 자동 Wi-Fi 확인을 켜거나 끌 수 있습니다.
2. 수동 확인은 현재 인터넷 연결을 사용합니다. 오프라인에서는 **서명된 자료 파일 가져오기**로 공식 자료 ZIP을 선택할 수 있습니다.
3. 공개 키 서명, 유효기간, 버전, ZIP 구조, 각 파일의 SHA-256·크기, 원자료 메타데이터와 실제 행 형식을 모두 검증합니다.
4. 검증을 마친 한 묶음 전체를 적용하고 다시 검사합니다. 실패한 외부 자료는 활성 자료를 덮어쓰지 않습니다.
5. 자료가 만료되거나 원자료 수집 후 30일이 지났거나 기기 시각을 신뢰할 수 없으면, 기존 자료로 참고 검사는 유지하고 자동 삭제 확인창 연결을 보류합니다. 수동 설정 확인·백신 추가 검사 안내는 유지합니다.

원자료 수집 날짜와 업데이트 묶음 발행 날짜는 따로 기록합니다. 오래된 목록에 새 발행 날짜만 붙여 최신 자료처럼 표시하지 않습니다. 저장된 서명 자료가 만료되어도 조용히 더 오래된 내장 목록으로 되돌리지 않습니다. 저장 파일의 서명·형식 검증 자체가 실패하면 내장 자료로 제한된 검사를 시도하고 오류를 표시하며 자동 삭제 연결을 막습니다.

기존 별도 MVT 목록은 호환성 관측 자료로 남지만, v1.3의 자동 삭제 판단은 현재 선택한 통합 참조 자료와 재검증 결과를 따릅니다. 그 결과 갱신 자료에서 철회한 지표가 구형 목록의 삭제 경로로 되살아나지 않도록 합니다.

## 검증과 저장 설계

`CatalogUpdateVerifier`는 호스트에서도 실행하는 순수 Java 검증기입니다. `CatalogUpdateStore`가 비공개 디렉터리에서 활성 자료와 이미 수락한 버전을 보관하고, `CatalogUpdateManager`가 Android 파일 선택/HTTPS 다운로드 및 앱 자산과 연결합니다. `MalwareInspection`은 검사 전체에서 한 개의 변경되지 않는 데이터베이스 선택을 사용합니다.

- ZIP은 압축 상태 최대 8 MiB, 실제 자료 합계 최대 16 MiB입니다. 메타데이터는 1 MiB, 서명 대상 manifest는 16 KiB 이하입니다.
- 멤버는 `manifest.json`, `manifest.sig`, `malware_catalog.json`, 네 개의 출처별 TSV, ClamAV 전용 allow TSV 순서로 고정됩니다. 파일을 디스크 경로로 추출하지 않습니다.
- 중앙 디렉터리와 로컬 헤더의 이름·순서·범위·압축 방식·크기·CRC/descriptor를 대조합니다. 경로 이동, 누락·추가 멤버, 겹친 오프셋, 뒤에 붙인 데이터, ZIP64, 암호화 및 주석은 허용하지 않습니다.
- manifest 원문 앞에 `RefurbCheck catalog update v1\0` 도메인 구분자를 붙여 `SHA256withRSA`로 검증합니다. JSON을 재직렬화한 결과가 아니라 수신한 원문 바이트를 검증합니다. 공개 키는 APK 자산에 포함되며 소스의 SHA-256 핀과도 대조합니다.
- 서명을 확인한 뒤 JSON 중복 키·형식·깊이 제한을 확인하고, 여섯 자료 파일의 SHA-256·크기를 각각 검증합니다. 각 TSV의 실제 파서 실행을 마쳐야 새 자료가 활성화됩니다.
- 출처는 기존 네 개로 제한됩니다. ClamAV allow 자료는 ClamAV 서명에만 적용되며 다른 독립 출처를 무효화하지 않습니다.
- 이전에 수락한 번호보다 작은 번호는 거절합니다. 같은 번호는 ZIP SHA-256까지 같아야 하며 다른 내용이면 충돌로 거절합니다.
- 활성 ZIP은 임시 파일을 완성하고 동기화한 다음 같은 디렉터리에서 원자적으로 이름을 바꿉니다. 파일별로 한 개씩 교체하지 않아 서로 다른 버전의 목록이 섞이지 않습니다. 지원하지 않는 파일시스템에서 비원자적 복사로 낮추지 않습니다.
- 활성 파일과 별도 버전 보관 파일을 유지합니다. 새 활성 파일을 적용한 뒤 버전 기록 전에 앱이 종료된 경우, 다음 읽기에서 서명된 활성 파일의 번호를 통해 복구합니다. 저장 오류는 보고하며 자동 조치를 보류합니다.
- 최신 자료를 적용한 이후 삭제 직전 재검증에서 데이터베이스 지문이 바뀌면 삭제를 보류하고 재검사를 요구합니다. 검증 마지막 시점에도 만료·시각 상태를 다시 확인합니다.
- HTTPS 연결은 고정 호스트와 시스템 인증서 검증을 사용하며 리디렉션을 따르지 않습니다. 연결/읽기 시간 제한과 전체 작업 예산을 적용합니다. 네트워크 작업은 전경에서만 호출합니다.

### 보장하지 않는 범위

TUF의 rollback/freeze/mix-and-match/endless-data 위협 분류를 참고했지만 **TUF 구현·준수 제품이 아닙니다**. 하나의 업데이트 키를 사용하며, 서명 임계값·별도 온라인 timestamp 역할·원격 키 폐기·키 교체 프로토콜을 제공하지 않습니다. 키가 유출되면 새 APK에 신뢰할 수 있는 공개 키를 포함해 배포해야 합니다.

시간은 기기 시계를 기준으로 합니다. 독립된 신뢰 시간 서버가 없으므로 침해된 OS가 시간을 속이거나 앱 비공개 데이터를 함께 되돌리는 공격을 막았다고 주장하지 않습니다. 앱 데이터 삭제/앱 제거 시 이미 수락한 버전 기록은 사라지고, 새 설치 APK의 기본 버전부터 다시 시작합니다. 앱의 프로세스 중단에 대한 원자적 파일 교체를 사용하지만 모든 저장장치의 전원 장애·펌웨어 오류를 보증하는 것은 아닙니다.

별도 버전 보관 기록 자체가 손상된 경우에는 자동으로 기록을 지우거나 낮은 번호로 되돌리지 않습니다. 일반 자료 재가져오기도 거절합니다. 보고서를 보관한 뒤 사용자가 앱 저장공간을 초기화하거나 재설치하면 다시 시작할 수 있지만, 이때 이전 수락 버전 기록도 사라집니다. 손상된 활성 ZIP만 있고 버전 기록은 정상인 경우에는 해당 기록 이상 번호의 정상 서명 자료로 복구할 수 있습니다.

서명 검증은 배포자와 자료 내용의 연결을 확인합니다. 자료의 완전성, 오탐률, 악성코드 부재나 게시자의 판단이 항상 옳다는 것을 증명하지 않습니다. 이 배포물에는 완전한 ClamAV 엔진, ESET 엔진, YARA-X 실행기, ML 모델이 들어 있지 않습니다.

## 게시자가 새 자료를 만드는 절차

`tools/sign_catalog_update.py`는 원자료를 인터넷에서 자동 수집하지 않습니다. 먼저 기존 선정 규칙과 출처별 라이선스에 따라 원자료를 검토하고 TSV/메타데이터를 일관되게 갱신해야 합니다. 원자료 날짜를 임의로 현재 날짜로 바꾸지 마세요. 같은 해시의 철회·오탐 수정·출처별 제외 자료도 검토합니다.

```bash
python3 tools/sign_catalog_update.py \
  --private-key /private/refurbcheck/catalog-update-private.pem \
  --sequence 2 \
  --created-at 2026-11-08T00:00:00Z \
  --expires-days 30 \
  --output data/catalog-updates/catalog-update.zip

bash tests/run_catalog_update_tests.sh
```

예시 날짜와 번호는 실제 발행 시각 및 단조 증가하는 번호로 교체합니다. 개인 키는 저장소 바깥에 보관하고 POSIX 환경에서는 `0600` 이하 권한을 적용합니다. 도구는 개인 키를 ZIP/APK/소스에 넣지 않습니다. 최초 공개 키/기본 버전 생성용 `--initialize-trust`는 이미 있는 신뢰 설정을 덮어쓰지 않으며, 일반 자료 갱신에는 사용하지 않습니다.

생성한 ZIP, `.sha256`, 읽을 수 있는 manifest, 해당 자료의 출처·라이선스·변환 소스를 함께 검토하여 공개 저장소에 배포합니다. `catalog-updates` 브랜치의 루트 ZIP을 바꿔야 앱 고정 주소가 새 묶음을 가리킵니다. 무해한 테스트 서명/샘플을 운영 목록에 넣지 않습니다. 게시 자동화에 개인 키를 커밋하지 않습니다.

## 확인한 테스트 범위

`tests/run_catalog_update_tests.sh`는 일시적인 테스트 키와 무해한 텍스트 목록으로 다음을 확인합니다.

- 정상 묶음, 서명 변조·다른 키·약한 키·도메인 구분자 누락
- 롤백·동일 번호 다른 내용·유효기간 경계·미래 시각·오래된 원자료 재발행
- 잘못된 JSON/UTF-8, 과대 입력, 파일 크기·해시·출처·개수·목록 지문 불일치
- ZIP 누락·추가·경로 이동·디렉터리·중앙 디렉터리 불일치·겹침·절단·붙임 데이터
- 저장된 정상 자료를 유지하는 실패 경로, 원자적 적용, 별도 버전 기록 복구, 손상된 활성 파일 복구
- 실제 최초 배포 ZIP과 공개 키의 고정 지문 및 내장 목록의 동일성

이 테스트는 전송·검증·저장 규칙의 회귀 검사입니다. 실제 갤럭시의 악성코드 탐지율이나 모든 네트워크·저장장치 동작을 측정한 실기기 시험은 아닙니다.
